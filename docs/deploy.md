# Выкатка в продакшен

Схема — один сервер, всё в Docker Compose (`infra/compose.prod.yaml`):

```
Интернет ──443/80──▶ Caddy (HTTPS, Let's Encrypt) ──▶ web (Next.js) ──▶ api (FastAPI)
                                                                           │
                         worker ◀── Redis (очередь)                        ▼
                           └──────────▶ PostgreSQL + pgvector ◀────────────┘
                           └──────────▶ SeaweedFS (закрытые снимки фидов)
```

Наружу открыты только 80/443. API, база, Redis, хранилище снимков, `/internal/*`, `/docs` снаружи
недоступны. Внутренние операции — через SSH на сервер (`fashion-worker …`, см. operations.md).

> Сейчас в каталоге только демо-данные. Публичный запуск — это демо-стенд, а не поиск по рынку.

## 1. Что купить

**Сервер (VPS)** — для этапа 1 с демо-каталогом и до ~50 тыс. предложений хватит:

| | Минимум | Комфортно |
|---|---|---|
| CPU | 2 vCPU | 4 vCPU |
| RAM | 4 ГБ | 8 ГБ |
| Диск | 40 ГБ SSD/NVMe | 80 ГБ NVMe |
| ОС | Ubuntu 24.04 LTS | Ubuntu 24.04 LTS |

Когда подключится OpenSearch (этап 3) и каталог вырастет к 500 тыс. — 4–8 vCPU и 16 ГБ RAM; цифры
нужно подтвердить нагрузочным тестом (раздел 12 ТЗ).

Где брать: для аудитории в России разумно размещать сервер в РФ — в поисковых запросах могут
встречаться персональные данные (152-ФЗ, локализация). Подойдёт любой провайдер с обычной VPS и
Ubuntu 24.04 (например, Selectel, Timeweb Cloud, Yandex Cloud, VK Cloud). Обязательно — снапшоты
или бэкапы дисков у провайдера и публичный IPv4.

**Домен** — любой регистратор. Нужна A-запись `домен → IP сервера` (и `www`, если нужен редирект).

## 2. Подготовка сервера (один раз)

1. При создании VPS добавьте свой SSH-ключ.
2. Под root:

   ```bash
   curl -fsSL https://raw.githubusercontent.com/fryggr/shmot/main/infra/server/setup.sh -o setup.sh
   bash setup.sh
   ```

   (если репозиторий приватный — скопируйте файл через `scp`). Скрипт ставит Docker, создаёт
   пользователя `deploy`, включает файрвол (22/80/443), запрещает вход по паролю, добавляет swap и
   автообновления безопасности.
3. Под `deploy` дайте серверу доступ на чтение к репозиторию (deploy key в GitHub:
   `ssh-keygen -t ed25519` → Settings → Deploy keys) и склонируйте:

   ```bash
   git clone git@github.com:fryggr/shmot.git ~/shmot && cd ~/shmot
   cp .env.prod.example .env.prod && chmod 600 .env.prod
   # заполнить DOMAIN, ACME_EMAIL и секреты: openssl rand -hex 32
   ```

## 3. Первый запуск

DNS уже должен указывать на сервер (иначе Let's Encrypt не выдаст сертификат):

```bash
./infra/server/deploy.sh main
```

Скрипт подтягивает ветку, собирает образы, поднимает стек и ждёт готовности API. Сервис `init`
применяет миграции и импортирует демо-фиды. Проверка: `https://<домен>`.

Ежедневный бэкап (cron пользователя `deploy`, `crontab -e`):

```
17 3 * * * cd ~/shmot && ./infra/server/backup.sh >> ~/backup.log 2>&1
```

Бэкапы лежат в `/var/backups/fashion` (14 последних). Их нужно ещё и уносить с сервера —
включите бэкапы/снапшоты у провайдера или копируйте файлы в объектное хранилище провайдера.
Перед beta проверьте восстановление: `./infra/server/restore-check.sh` (разворачивает последний
бэкап во временную базу, боевую не трогает).

## 4. Обновления и откат

```bash
cd ~/shmot && ./infra/server/deploy.sh main
```

Перед обновлением делается бэкап. Миграции применяются автоматически и вперёд; откат кода —
`git checkout <прежний коммит> && ./infra/server/deploy.sh`, но если новая миграция уже изменила
схему, сначала восстановите базу из бэкапа, сделанного перед деплоем.

## 5. Что проверить перед публичным запуском

- [ ] Страницы открываются по HTTPS, `http://` редиректит на `https://`.
- [ ] `https://<домен>/internal/imports` и `/docs` → 404.
- [ ] Бэкап создаётся по cron, `restore-check.sh` проходит.
- [ ] Секреты в `.env.prod` сгенерированы, файл `chmod 600`, не в git.
- [ ] Мониторинг доступности: внешний пинг `https://<домен>/` (UptimeRobot, Яндекс Мониторинг и т.п.).
- [ ] Политика конфиденциальности и согласие (поисковые запросы хранятся 30 дней) — до публичной beta.

## Ограничения текущей сборки

- Один сервер, без резервирования: падение VPS = простой до восстановления.
- Rate limit — в памяти каждого процесса API (`API_WORKERS` процессов → лимит на процесс).
- Метрики и алерты из раздела 13 ТЗ (stale source, outbox lag, p95) пока не собираются
  автоматически — только логи и `fashion-worker reconcile`.
- Образы собираются на сервере. Позже — сборка в CI и публикация в реестр образов.
